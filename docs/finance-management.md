# 财务管理：实施需求与使用说明

## 补充后的实施提示词

基于现有 Vue 前端和 Gin/GORM 后端，实现个人日常记账闭环。沿用 `internal/app` 组装、显式迁移、JWT 认证及共享 Capability，不增加另一套 AI 业务逻辑。参考成熟产品的账户、交易、分类和转账设计，以“快速记录钱花在哪里”为首要目标。

1. 支持银行卡、支付宝、微信、现金等账户，开户填写期初余额。支持收入、支出、账户间转账、交易日期、商户、分类、说明。提供默认分类、自定义分类、筛选分页、月度收支和分类分析。
2. 金额以整数分存储，对外使用两位小数字符串；不允许浮点金额、超精度或负流水金额。内部转账在一个事务中修改两个账户，不能被计算为收入或支出。期初余额不作为当期收入。
3. 用户只能访问自己的账户、分类、流水、快照与事件；管理员也没有跨用户财务访问特权。PATCH 使用经校验的白名单 map，支持 false、0、空说明和分类置空，未提交字段保持原值。
4. 提交必须包含稳定幂等键，网络重试不能重复记账。普通流水支持修改金额、账户、类型、日期时间及优惠；在同一事务内冲销旧余额影响并按新值入账，返现子项保留身份同步调整。已有退款不得将原支出改为其他类型、迁移账户、缩减至累计退款以下或晚于退款日期；分期、退款及返现子项的财务字段通过原业务维护。作废冲销余额并保留原流水。保留来源、状态、账户余额快照与操作事件。
5. AI 通过现有工具调用系统查询账户、分类、流水和统计，并创建结构化待确认草稿；金额、账户、日期不明确时先询问。AI 不能确认或作废流水、直接修改余额。用户在财务页面核对后确认，后端才能入账。
6. 恢复现有前端的账户、流水和总览，移除尚未实现的入口，完成业务、HTTP 和模拟 AI 对话集成测试。新表不自动接管历史归属不明的数据。

## 设计依据

调研日期：2026-09-26。以下是产品机制参考，不涉及投资或借贷建议。

- [YNAB：添加交易](https://support.ynab.com/en_us/how-to-add-transactions-in-ynab-HyDwA_byi?mobile-help=true)：交易围绕金额、账户、收款方和分类组织。本次沿用原页面字段，补齐默认分类与快速录入。
- [Actual：内部转账](https://actualbudget.org/docs/transactions/transfers/)：需要明确关联转出与转入账户，避免转账污染收支报表。本实现用单条转账流水和同一数据库事务保证两端一致。
- [Actual：交易导入与重复检测 API](https://actualbudget.org/docs/api/reference/)：导入需要考虑重复数据。本次采用明确的 requestId 精确幂等，不根据“同金额、同商户”直接合并，避免误删真实的重复消费。
- [Actual：收款方与默认分类](https://actualbudget.org/docs/transactions/payees/)：商户和分类关联能减少填写工作。本次保留商户字段、默认分类、AI 分类入口。
- [Actual：拆分交易](https://actualbudget.org/docs/transactions/split-transactions/)：单笔消费可分摊多个分类，适合后续扩展；当前每笔流水只有一个分类。

AI 草稿确认、白名单 PATCH、用户级事务锁和精确金额属于本项目的实现决策，不是上述产品全部具备的功能声明。

## 使用方式

启动后端时 `App.Initialize` 自动迁移新表。进入“财务管理”，先添加账户并填写当前余额，随后记录新增收支。首次开户且尚无分类时，自动创建餐饮、交通、购物、居住、生活缴费、医疗、工资及其他收入分类。

在“AI 对话”中选择已配置的、支持工具调用的模型，例如：“2026 年 9 月 26 日，用现金账户付午餐 25.50 元，帮我记账”。AI 查询实际账户 ID、生成草稿后，进入“财务管理 → 流水”，按“待确认”筛选，核对并点击“确认入账”。草稿不会影响余额或统计。错误草稿可作废；已入账错账也可作废，系统自动恢复关联账户余额。

账户编辑只能修改资料及统计开关。余额由期初余额和有效流水决定；需要修正期初错误时，应作适当的更正流水并注明原因。账户允许负余额，体现账本事实，不代表实际银行额度或付款授权。

删除账户采用软删除（内部仍使用 archived 标记），允许正余额、零余额和负余额，删除后退出账户列表及当前资产统计，保留余额、流水、快照和转账关联。若有待确认流水，须先确认或作废，影响接口返回 pending 数量。冲销旧流水只修正历史余额，不重新显示已删除账户。Web 第三栏与 iOS 确认弹窗均说明余额及保留历史的行为。

2026-09-27 账户删除交互复核：参考 [YNAB 的关闭与删除区分](https://support.ynab.com/how-to-close-or-delete-an-account-in-ynab-ry_409Gko)，采用保留历史的软删除语义；YNAB 的关闭需结清余额，本项目不采用这一预算限制，也不生成虚假的清零流水。历史收支报表继续包含已删除账户的已入账记录。iOS 左滑使用红底垃圾桶图标、无障碍账户名称，并关闭整行滑动触发；确认按钮简写为“删除”。显式设置红色以避免继承页面青色，依据 [Apple SwiftUI swipeActions](https://developer.apple.com/documentation/swiftui/view/swipeactions(edge:allowsfullswipe:content:)) 的 destructive role 与 tint 用法。若仍看到“请先转出余额”旧报错，需要核对客户端所连接的后端是否已更新，当前源码不再包含此限制。

当前金额币种仅为 CNY，不做汇率换算。日期保存 `YYYY-MM-DD`，月度统计按 UTC+8；未来日期的已入账流水会立即影响账户余额，在所属月份计入收支，不表示预约付款。

## HTTP 契约

所有路径以 `/api/finance` 开头且必须携带现有 Bearer JWT。成功返回 `200 {"data": ...}`。参数错误 400、不可见/不存在 404、状态或幂等冲突 409、内部失败 500，内部错误不返回数据库细节。

| 方法 | 路径 | 行为 |
| --- | --- | --- |
| GET / POST | `/accounts` | 查询有效账户 / 开户 |
| PATCH | `/accounts/:id` | 局部更新账户资料 |
| GET | `/accounts/:id/impact` | 流水和余额快照数量 |
| DELETE | `/accounts/:id` | 账户软删除，允许非零余额，保留历史 |
| GET / POST | `/categories` | 查询 / 创建自己的分类 |
| GET / POST | `/transactions` | 查询流水 / 人工直接入账 |
| PATCH | `/transactions/:id` | 更正分类、商户、说明 |
| POST | `/transactions/:id/confirm` | 确认自己的 AI 草稿 |
| POST | `/transactions/:id/void` | 草稿作废或已入账流水冲销 |
| GET | `/overview` | 账户资产、六个月收支、本月分类汇总 |
| GET | `/events` | 最近 100 条操作事件 |

开户示例：

```json
{"name":"现金","accountType":"cash","currency":"CNY","balance":"100.00","includeInNetWorth":true}
```

人工记账示例（账户 ID 使用自己的查询结果）：

```json
{
  "requestId":"expense-20260926-001",
  "accountId":1,
  "type":"expense",
  "amount":"25.50",
  "transactionDate":"2026-09-26",
  "counterparty":"午餐",
  "description":"工作日午餐"
}
```

- `requestId` 必填，8–96 位字母、数字、连字符或下划线，按用户隔离。同键同内容同来源返回原流水；内容或来源不同返回 409。重放不会改变余额，但会记录调用事件。UI 在同一录入会话内对同一载荷复用键；关闭页面后再次录入会视为新消费。
- 流水金额必须为正数；金额和账户余额绝对值上限 `1000000000000.00`，精度两位小数。数据库存储 `BIGINT` 分，只有绘图和展示比率使用浮点运算。
- 转账指定 `type=transfer` 与不同的 `targetAccountId`，不得指定分类。`targetCreditCardId` 只接受缺省或 null，信用卡业务未启用。
- 分类可缺省或 null；指定时必须属于自己且与收支类型匹配。
- 流水 PATCH 仅接受 `categoryId`、`counterparty`、`description`。`categoryId=null` 清空分类，空字符串清空文本。已作废记录不可编辑。
- 账户 PATCH 接受 `name`、`accountType`、`institution`、`maskedAccountNumber`、`currency`、`includeInNetWorth`、`sortOrder`、`notes`。`balance` 仅开户可写，`availableBalance` 为派生返回值，等于余额，不可独立提交。
- 卡号输入只保留尾四位，不保存完整卡号。

流水筛选：`startDate`、`endDate`（含边界）、`type`、`accountId`（包含转入方）、`categoryId`、`minAmount`、`maxAmount`、`keyword`（商户、说明字面子串）、`status`、`limit`、`offset`。默认 100 条、最多 500 条，按交易日期及 ID 倒序。前端合计明确标为“当前页已入账合计”；总览基于数据库全部记录汇总，不受列表分页影响。默认查询包含 pending/posted/voided 三种状态。

`overview` 的负债字段仅代表计入统计账户的负余额，不能理解为全部现实负债。`netWorthTrend`、`upcoming` 保留为空数组以兼容旧类型，页面不绘制未实现的历史净资产或贷款计划。快照用于保留余额变更证据，不伪造历史净资产。

## AI 与事务架构

```text
HTTP 财务 Handler ───────────────────┐
                                    ├─ finance.Service.Execute → 用户权限、校验、事务 → GORM
AI 对话 → Capability → 财务工具适配 ──┘
```

注册的工具为 `finance.account.list`、`finance.category.list`、`finance.transaction.list`、`finance.transaction.create`、`finance.overview`。工具携带 JSON Schema，但最终校验始终在 Service。工具参数不能指定 owner 或 source；可信 Actor 和来源由调用入口提供。

工具创建的流水强制 `pending`。模型不能获得确认、作废、账户开户或账户更新工具。即使内部代码错误地使用 AI 来源调用确认/作废，服务也会拒绝。AI 对话结果会按既有 actions 契约记录工具成功或失败。

同一用户的业务事务先锁定用户行，在 MySQL/InnoDB 下串行处理余额、唯一幂等键及状态转换。两端余额、流水状态、快照及审计同事务提交，任一步失败全部回滚。重复确认、重复作废不会重复变更余额。此实现也对查询加相同用户锁，优先保证简单一致的个人账本；大规模报表可后续改为只读一致性事务。

业务测试覆盖精度、权限与关联归属、PATCH 零值/空值、幂等冲突、余额溢出完整回滚、分页、分类、统计排除转账、AI 草稿、重复确认及作废。应用测试使用真实 Gin 路由、JWT、临时 SQLite、模拟模型 HTTP 传输，验证 AI 草稿与人工确认共用账本。没有调用真实模型、连接真实 MySQL 或部署；SQLite 不能证明 MySQL 行锁行为，正式发布前应在目标 MySQL 做并发验收。

后续独立扩展：拆分交易、退款关联、预算、票据附件/OCR、银行账单导入与对账、多币种、信用卡/贷款/房贷，以及基于快照与历史配置的净资产趋势。原贷款与房贷组件保留源码，本次不开放入口。

## 周期记账、模板与转账手续费（2026-09-28）

Web 和 iOS 的“流水 → 模板与周期”管理模板及计划。“记录流水 / 记一笔”可选择保存为流水、模板或周期计划；模板仅保存填写内容，使用时预填并采用当天日期，用户可修改后入账，每次使用产生独立幂等键。

周期支持每天、每周、每月、每年，包含开始日期、可选截止日期（含当日）、暂停、恢复与删除。采用 UTC+8 自然日，到期生成待确认流水，不直接改变余额；确认后才入账。每月 31 日在短月取月末，之后恢复 31 日；2 月 29 日的年度计划在非闰年取 28 日。服务启动及每分钟检查到期计划，停机或暂停期间的遗漏期次在恢复后补齐，每计划每批最多 120 期。删除计划保留已生成流水，作废某一期不会重新生成该期。更改金额、账户或周期时删除旧计划后新建，历史不变。账户或分类失效时停止该计划的生成并显示错误。

转账金额表示转入金额，手续费由转出账户额外支付：转账 100 元、手续费 2 元，转出减少 102 元，转入增加 100 元。手续费以流水 `fee` 字段保存，计入月度支出、分类“转账手续费”和列表支出合计；本金不计入收支。两端余额、手续费、快照同事务提交，确认和作废幂等，作废一并退回手续费。当前仍只支持 CNY，不能跨币种转账，不连接银行或发起真实支付。

新增接口：`GET/POST /api/finance/presets`、`PATCH/DELETE /api/finance/presets/:id`、`POST /api/finance/recurring/materialize`（正文 `{}`）。创建字段：`key`（8–96 位稳定幂等键）、`name`、`transaction`（标准流水字段，日期可省略）、`frequency`（空字符串表示模板，或 daily/weekly/monthly/yearly）、`startDate`、`endDate`。PATCH 白名单为 `name` 与 `enabled`，通过 map 更新并支持 false。计划返回 `nextDate`、`lastError`，生成流水来源为 `recurring`。AI 无权管理模板及计划；所有关联均校验当前用户归属。

迁移新增 `finance_presets_v2` 表及流水 `fee` 字段，旧流水手续费默认为 0。验证覆盖费用入账/冲销/溢出回滚、统计、模板与计划幂等、暂停恢复、月底闰年、权限隔离、删除保留历史及真实 HTTP 路由。后台多实例依赖现有 MySQL 用户行锁；SQLite 测试不代替生产 MySQL 并发验收。

## 还款优惠返现（2026-09-28）

Web 第三栏和 iOS 转账表单支持优惠金额、优惠到账账户和已到账／待到账状态。转账本金不受优惠影响：还款 1,000 元、优惠 1 元，仍从原账户转出 1,000 元、信用卡到账 1,000 元，再单独生成 1 元“还款优惠”收入。到账账户默认转出账户，也可选择自己的其他可记账账户；手续费继续从转出账户额外支付，计入支出。

创建请求可传 `rebate`（非负金额字符串，仅限转账）、`rebateAccountId`（省略时为转出账户）、`rebatePending`（默认 false）。零优惠不能携带到账账户或待到账标记。转账记录保存这些设置，收入通过只读 `rebateParentId` 关联原转账；模板和周期计划保留优惠设置。旧流水优惠默认 0，迁移通过现有 AutoMigrate 添加字段及关联唯一索引。

已到账优惠随转账在同一事务入账；待到账优惠生成待确认收入，不提前改变余额或统计，确认时以 UTC+8 当天作为到账日期。AI 和周期生成的转账草稿确认后才生成关联优惠。独立收入参与账户筛选、收入分类和净资产计算，不抵减还款本金或手续费。原转账作废时一并冲销已到账优惠、取消待到账优惠；优惠不能单独作废。重复创建、确认和作废不重复改变余额，任一关联账户越权、不可用或余额溢出均完整回滚。

### 支出优惠

创建流水与模板支持 `discount`（十进制金额字符串，默认 0），仅支出可使用，必须非负且小于提交的原金额 `amount`。流水保存后的 `amount` 为实付，`discount` 保留优惠金额；账户扣款、收支统计、退款上限和分期本金以实付为准。模板内 `amount` 仍为原金额，生成流水时减免一次。转账继续使用 `rebate` 独立返现逻辑。

标签已退出业务模型，新建、编辑、搜索及模板不再接受或传播该字段；历史数据库列不再映射读取，未物理删除历史列。

## 消费分期的生成范围与额度

- `periods` 为 2–480；`startPeriod` 为 1–总期数，旧请求省略或传 0 时从第 1 期生成。日期仍以 `firstDate` 为第 1 期基准，跳过的期次不生成流水、不计收支和余额。`total` 是实际生成范围内的本息合计，进度分母使用实际生成账单数。
- `debtMode`：`spread`（省略时同义）在每期入账时计入欠款；`upfront` 在创建时预记实际生成范围内本金，每期确认仅补记利息欠款，收支统计仍以该期完整本息入账为准。
- `restoredCredit` 是可选非负金额字符串，不得超过实际生成范围内本金。剩余恢复额只增加可用额度；每期本金入账后抵扣恢复额，最低为 0，不改总授信、余额或收支。
- `interestCreditMode`：`spread`（省略时同义）不提前预留利息；`upfront` 从创建时预留实际生成期次中尚未入账的利息，每期入账后释放对应预留，避免与已体现在余额中的利息重复占用。与 `interestMode`（分期／首期计入收支）独立。
- 账户列表返回只读派生金额 `installmentCredit` 和 `installmentInterestReserved`。可用额度 = 总授信 + 账本余额 + 剩余专项恢复额 − 未入账利息预留；两者不作为账户可编辑字段。
- 新规则写入原分期计划 JSON，与余额冲回、预记本金、生成子账单共同提交；同参数重试复用计划，重复确认不会重复扣款。
