# 个人助手后续设计

以下为规划，不代表当前已实现；当前结构见 [架构说明](../architecture.md)。

用户与登录
- 用户表：账号、密码哈希、昵称、时区。
- 注册、登录、获取当前用户接口。
- 认证中间件：验证登录凭证，向业务层提供可信的用户 ID。
- 暂时不用做复杂角色、后台用户管理。

会话与消息
- 创建会话、保存消息、查询会话历史。
- 每个会话归属一个用户，每条消息归属一个会话。
- 校验用户只能访问自己的数据。

最小 AI 对话
- 组装用户消息、时间、最近对话。
- 调用模型，保存并返回回答。
- 先实现连续对话。

工具调用
- 先接一个查询工具，比如查待办。
- 跑通“模型提出调用 → 后端执行 → 结果交回模型”的循环。

用户记忆
- 加入记忆提取、保存、更新和读取。
统一用户入口：所有文字、语音、App 请求统一转换为 UserMessage，进入 Agent Runtime。
 2. 构建上下文 Context：加载当前用户、当前时间、最近对话、当前项目、用户偏好、相关记忆等信息。
    接收消息：后端从登录凭证确定用户，读取时间、时区、最近对话和历史摘要。
    加载用户画像：从 MySQL 获取已记录的个人信息、兴趣和习惯，例如“不喜欢早起”。画像少时直接加载，变多后再筛选相关内容。
    交给模型：发送用户原话、上述背景，以及可用工具的说明和参数格式。
    按需查询：模型提出工具调用，后端校验权限、执行查询，再将结果交回模型；信息不足则继续查或追问。
    生成回答：模型结合业务数据和用户画像回答，后端保存对话并返回应用端。

AI 理解请求：将 UserMessage + Context 交给 LLM，不强制识别单一 Intent，而是输出 Goal 和用户真正想完成的事情。

目标拆解：AI 将 Goal 拆成多个 SubTask，例如“查询本周完成事项”“查询下周待办”“查询下周日程”。

能力发现：通过 SkillRegistry / ToolRegistry 查找每个 SubTask 可以使用的能力，例如 task.search、calendar.search、project.search。

生成执行计划 Plan：形成结构化 ExecutionPlan，明确调用什么 Tool、参数是什么、哪些可以并行、哪些存在依赖。

执行 Tool：Agent Runtime 按 Plan 调用 Tool，Tool 再调用真正的 Go Service，例如 TaskService、CalendarService。

业务层执行：Go Service 负责权限、参数校验、事务、数据库操作等确定性业务逻辑，AI 不直接操作数据库。

结果回传 AI：Tool 将结构化 ToolResult 返回 Agent，AI 判断结果是否足够、是否存在冲突或缺失信息。

动态 Re-Plan：如果信息不足，AI 可以继续调用其他 Tool；如果关键条件缺失，则询问用户，而不是强行执行。

生成最终回答：AI 对多个 ToolResult 进行汇总、去重、排序、优先级判断，生成自然语言回复。

记忆与事件记录：保存必要的对话上下文、用户确认事项、执行结果和操作日志，为下一轮对话提供 Context。

整体代码链路：User → AgentRuntime → Context → LLM → Goal → Planner → Skill/Tool → Service → Repository → Result → LLM → Response → Memory。
